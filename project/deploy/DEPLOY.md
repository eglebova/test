# Инструкция по деплою

## 1. До размещения

1. Выбрать и зарегистрировать домен на аккаунт владельца; включить MFA у регистратора и DNS-провайдера.
2. Выбрать хостинг/сервер с инфраструктурой в РФ. Проверить регион хранения файлов, технических журналов и резервных копий, субподрядчиков и порядок уведомления об инцидентах.
3. Убедиться, что владелец имеет отдельные административные доступы, а подрядчик не является единственным владельцем аккаунта.
4. Проверить биографические сведения, реестровый статус, название образования, направления практики и все публичные формулировки.
5. Зафиксировать позицию АПМО по отсутствию публичного адреса и актуальным требованиям к сайту/продвижению.
6. Определить оператора и фактические потоки персональных данных. Даже без форм сервер и хостинг могут обрабатывать IP, время, URL и технические журналы. Не публиковать выдуманную политику.

## 2. Публичный каталог

В архив уже включён каталог `dist/` — его содержимое можно использовать для первичного тестового размещения. Перед production-публикацией с выбранным доменом рекомендуется пересобрать каталог, чтобы сформировать canonical и sitemap. На рабочем компьютере выполните:

```bash
python3 scripts/build.py --origin https://ваш-домен.ru
```

Скрипт создаст `dist/`. Если проверка завершилась `FAIL`, не публикуйте каталог до устранения ошибок. Не копируйте на сервер весь исходный архив.

## 3. Подготовить сервер

Рекомендуемый вариант: поддерживаемый Linux LTS, Nginx или Caddy, отдельный непривилегированный системный пользователь, только SSH-ключи, запрет SSH root/password login, firewall с минимальным набором портов. Административный SSH по возможности ограничить доверенными IP или VPN.

Открытые порты на публичной стороне: 80/tcp и 443/tcp. SSH-порт — только с необходимым ограничением доступа. Не запускать панели управления и тестовые службы в публичном доступе.

Пример структуры релизов:

```text
/var/www/glebova-site/
  releases/
    2026-11-04-001/   # содержимое dist/
  current -> releases/2026-11-04-001
```

Создайте каталог и пользователя с минимальными правами. Не размещайте исходный проект, Git-репозиторий, файлы конфигурации, резервные копии и секреты внутри публичного web-root.

## 4. Загрузить файлы и настроить веб-сервер

Передайте только содержимое `dist/` в новый каталог релиза, например через `rsync` по SSH-ключу. Проверьте владельца и права чтения. Установите `deploy/nginx-site.conf` в конфигурацию сайта Nginx, заменив `example.ru` и пути к TLS-сертификату.

Для Nginx:

```bash
sudo nginx -t
sudo systemctl reload nginx
```

TLS-сертификат получите и настройте через выбранный доверенный механизм (например, Certbot или автоматическое TLS в Caddy). HTTP должен перенаправляться на HTTPS. Включайте HSTS только после проверки HTTPS для всех используемых поддоменов.

Альтернатива — `deploy/Caddyfile`. Не используйте два веб-сервера одновременно для одного virtual host.

## 5. Проверка после выкладки

Проверьте:

- главную страницу и все URL из `sitemap.xml`;
- canonical и `og:url` с фактическим доменом;
- `robots.txt` и `sitemap.xml`;
- корректный статус HTTP 404 на отсутствующем URL;
- телефон и почту на мобильном устройстве;
- редирект HTTP → HTTPS и автоматическое обновление сертификата;
- заголовки CSP, HSTS, X-Content-Type-Options, X-Frame-Options, Referrer-Policy и Permissions-Policy;
- отсутствие публичной доступности `.git`, `.env`, резервных копий, исходников и конфигураций;
- доступность из российских мобильных и фиксированных сетей.

## 6. Резервирование и обновление

Код храните в Git-репозитории в аккаунте владельца. Настройте ежедневное резервирование исходного кода, контента и конфигурации. Резервные копии шифруйте; ключ храните отдельно; как минимум одна копия должна быть изолирована от основного сервера. Не реже одного раза в квартал выполняйте тестовое восстановление и фиксируйте результат.

При выпуске новой версии сначала сохраните текущий релиз, затем загрузите новый каталог и переключите символьную ссылку `current`. Для rollback переключите её обратно на предыдущий релиз и проверьте сайт.

## 7. Аккаунты и почта

Включите MFA у регистратора, DNS, хостинга, Git и почты, где это поддерживается. Для почты используйте уникальный длинный пароль и проверьте восстановление доступа, правила пересылки, активные сессии и подключённые приложения. Не храните пароль или ключи в коде.

Владелец должен иметь прямой доступ к домену, серверу, DNS, Git, резервным копиям и платным подпискам.
